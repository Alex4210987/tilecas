# Reproduction entry points

Run from the repository root after [platform setup](INSTALLATION.md). The default output directory is `runs/`; it is excluded from version control. Configure a separate path with `KERNELBENCH_RUNS` when needed.

## Inspect without an accelerator

```sh
python3 scripts/run_experiment.py --help
python3 scripts/submit_kda_pair.py --help
python3 kernelopt/backends/rocm/submit_random.py --check-config
```

To exercise Ascend workspace staging without starting a model or device job, choose a new run identifier:

```sh
KERNELBENCH_STAGE="$PWD/work/staged" \
python3 scripts/run_experiment.py ours level3/1_MLP \
  --backend ascend --dry-run --run-id tilecas-mlp-preview
```

This creates a workspace only. Repeating it requires a new identifier. The generic launcher's operational path is Ascend; use the dedicated launcher below for the supported two-platform path.

## Configure and run a fresh workload

Obtain the external KDA resource checkout and set `KDA_SOURCE_DIR` as described in [KDA_REFERENCE.md](../KDA_REFERENCE.md). The current shared submission script checks these resources even when selecting the AKO-based `ours`, `fixed`, `native-only`, or `unrestricted` modes.

```sh
export KDA_ENV_SCRIPT="/absolute/path/to/accelerator-env.sh"
source "$KDA_ENV_SCRIPT"

# Check source, workload mappings, and prompt generation without device execution.
python3 scripts/submit_kda_pair.py check-all --platform ascend --mode pair
python3 scripts/submit_kda_pair.py check-all --platform rocm --mode pair

# Submit one TileCas run; this starts a real model/accelerator job.
python3 scripts/submit_kda_pair.py submit --platform ascend --device 0 \
  --task level3/1_MLP --model gpt-6-astra --mode ours
```

For ROCm, use `--platform rocm --device 0` with the ROCm environment activated. Use a model identifier supported by the installed agent service; the supplied launcher currently exposes `gpt-6-astra` and `deepseek-flash`. DeepSeek requires `--driver-home` pointing to its configured private driver directory. No model access is included with this source release.

The submission script registers runs before queueing, prevents duplicate active experiments, and measures the reference before optimization. A foreground supervisor applies the 7,200-second paper budget after device acquisition. When running a lower-level workflow directly, use `scripts/run_with_paper_budget.py --record /absolute/path/to/budget.json -- <foreground-command>`; wrapping a command that only queues another job does not limit that job.

`--register-only` stages and registers a queued run without starting the queue worker. Resume those exact paths with the launcher's `queue` action instead of submitting duplicates. Run state and generated artifacts remain in the local runs directory.

## Modes and scope

| Mode | Behavior |
| --- | --- |
| `ours` | AKO with the TileCas policy; one conversation across High and Low |
| `fixed` | Independent High search, validated export, then a fresh Low conversation |
| `native-only` | Native-source search |
| `unrestricted` | Base workflow with its multi-representation support |
| `kda` / `kda-ours` | KDA without / with TileCas |
| `pair` | Separate KDA and KDA+TileCas runs |

`ARM_CAPABILITIES.md` describes comparison definitions. Random routing uses a separate launcher described in `RANDOM_ROUTING.md`; that launcher has additional case-specific preflight requirements. The full paper's comparison definitions do not imply that every variant has a turnkey fresh-clone submission command.

Inside a generated experiment workspace, `bash scripts/bench.sh LABEL` evaluates a candidate, `python scripts/diagnose.py` supplies diagnosis when needed, and `python scripts/export.py --help` documents the platform export interface. These workspace scripts are generated by the launchers.

Hardware correctness, compiler compatibility, and performance must be measured on the selected platform. Source parsing and dry-run staging do not establish accelerator execution results.
